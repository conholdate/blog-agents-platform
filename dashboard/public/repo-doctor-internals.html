Issue types at a glance

What each rule catches, and how confidently it can be fixed without you.

TypeCatchesFixStrategy
DUPLICATE_KEY same source path appears more than once delete every occurrence but the last deterministic
INVALID_JSON file fails JSON.parse() strip a trailing comma before a closer, if that's the cause deterministic or llm-assisted
EMPTY_TARGET target is "" LLM proposes a destination, re-validated before use llm-assisted
MALFORMED_TARGET target has no leading / and no scheme prepend /, or https:// for a bare hostname deterministic
SELF_LOOP_REDIRECT source and target are the same path on this domain's own host delete the entry deterministic
CHAINED_REDIRECT target is itself another entry's source point straight at the final destination deterministic

What keeps this safe to run unattended

01

The LLM never decides what's broken. All six rules run on raw text alone; the LLM only phrases wording and, for two rule types, drafts replacement text.

02

Every draft is re-parsed before it can be shown. A bad LLM suggestion gets rejected in Phase 1 — this happened on the first real run against Redirects.json.

03

Preview and commit use the same bytes. Confirm never re-asks the LLM — it commits exactly what Phase 1 already validated and showed you.

04

A PR is the ceiling, not a commit. Nothing reaches master without a human merging it — same as PR #150.

05

Self-loop/chain checks only strip a domain's own host. A deliberate cross-subdomain redirect (blog → about) is left as a full URL instead of being collapsed to a bare path — found live in two different domains' files, where the old behavior would have deleted a real, working redirect.
